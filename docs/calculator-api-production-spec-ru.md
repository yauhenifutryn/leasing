## 1. Цель документа

Голосовой ассистент ("Ксения") уже интегрирован с публичным API калькулятора через endpoint `/1.0/calculate/`. На этапе MVP выявлен ряд системных ограничений API, из-за которых голосовой бот не может дать клиенту корректную и полную консультацию в реальном времени.

Документ описывает:
1. Текущее состояние API и его ограничения.
2. Какие проблемы это создаёт в живом диалоге (с примерами из записей звонков).
3. Предлагаемое целевое состояние API.
4. Обоснование, почему бизнес-логику (валюта, лимиты по предметам, правила возраста) целесообразно реализовать именно на стороне калькулятора, а не на стороне голосового бота.
5. Примерный контракт запросов/ответов для реализации.

Документ не является финальным ТЗ. Это обзор желаемого направления для совместного обсуждения и последующей детализации.

## 2. Текущее состояние API

### 2.1 Что есть сейчас

`GET /1.0/calculate/` принимает параметры через query string:

| Параметр | Тип | Пример | Обязательный | Комментарий |
|---|---|---|---|---|
| `client_type` | string | "Физическое лицо" | да | Принимает только "Физическое лицо" и "Юридическое лицо" (ИП не поддерживается отдельно) |
| `subject` | string | "Легковой автомобиль" | да | Ограниченный список значений |
| `condition_new` | int | 1 | да | 1 = новый, 0 = б/у |
| `age` | int | 3 | при condition_new=0 | Возраст предмета в годах |
| `currency` | string | "BYN" | да | BYN, USD, EUR |
| `cost` | number | 70000 | да | Стоимость в указанной валюте |
| `prepaid` | number | 30 | да | Аванс в процентах (0-100) |
| `term` | int | 36 | да | Срок в месяцах |
| `type_schedule` | string | "0" | да | "0" = аннуитет, "1" = убывающий |

### 2.2 Что возвращает API

**Успех (HTTP 200):**
JSON с данными расчёта (аванс в рублях, массив платежей, выкупной платёж, удорожание, URL с графиком).

**Ошибка (HTTP 404):**
Пустой ответ без тела. Голосовой бот не знает, что именно пошло не так.

**Ошибка (HTTP 4xx/5xx прочие):**
Текст без машинно-читаемой структуры.

### 2.3 Текущие ограничения, видимые голосовому боту

| Ограничение | Проявление | Ссылка на диалог |
|---|---|---|
| Физлицо + USD | HTTP 404, без причины | Звонок 18:07:02: клиент назвал 24300 USD, бот не смог объяснить отказ в двух фразах |
| Грузовик/спецтехника для физлица | Неизвестно: в документации нет, бот угадывает | Звонок 18:22:35 |
| Минимальный аванс | Не задокументирован формально | Бот считает "10%", клиент просит "0%", отказ непонятен |
| Максимальный срок | По таблице до 84 мес, по умолчанию бот ставит 36 | Звонок 18:11:27 |
| Тип графика (линейный) | Бот передаёт "1", но API не меняет поведение или возвращает тот же аннуитетный результат | Звонок 18:17:51, повторные попытки не дали линейного графика |

## 3. Проблемы, которые это создаёт на практике

### 3.1 Пример 1: отказ в валюте без объяснения

Клиент: *"Двадцать четыре тысячи триста долларов."* (физлицо)

Сейчас происходит: API возвращает HTTP 404 без тела. Бот не знает причину и выдаёт общую фразу *"По заданным параметрам условия лизинга не найдены"*. Клиент не понимает, что именно не так (валюта? сумма? предмет?).

Как должно быть: API возвращает структурированную ошибку вида *"физическое лицо может финансироваться только в BYN"*. Бот автоматически предлагает клиенту: *"Для физических лиц график только в белорусских рублях. Могу пересчитать: 24 300 долларов по курсу 3 рубля это примерно 72 900 рублей. Продолжаем?"*

### 3.2 Пример 2: недостижимый срок

Клиент: *"Хочу лизинг на 300 месяцев."*

Сейчас происходит: бот по системному prompt-у знает только "36 мес. по умолчанию", отвечает что "максимум 36". Это неверно: по таблице максимум 84 мес.

Как должно быть: API знает свои лимиты и возвращает ошибку с подсказкой *"максимум 84 мес. для этой комбинации"*. Бот говорит клиенту: *"Максимум для легкового авто физлицу 84 месяца. Посчитать на 84?"*

### 3.3 Пример 3: игнорирование типа графика

Клиент: *"Сделай линейный график."*

Сейчас происходит: бот вызывает API с `type_schedule=1`, API возвращает аннуитет без указания что запрос был изменён. Клиент три раза повторяет запрос, получает один и тот же результат.

Как должно быть: API либо выполняет линейный расчёт, либо явно сообщает *"линейный график недоступен для этой комбинации"*.

## 4. Предлагаемое целевое состояние

### 4.1 Структурированные коды ошибок

Любой неуспешный ответ должен содержать:

```json
{
  "ok": false,
  "error_code": "ADVANCE_BELOW_MIN",
  "message_ru": "Минимальный аванс для легкового авто возраст 6-10 лет составляет 15%",
  "violated_rule": "min_advance",
  "rule_context": {
    "subject": "Легковой автомобиль",
    "age_bracket": "6-10 лет",
    "min_advance": 0.15,
    "max_advance": 0.40
  },
  "suggestions": [
    {
      "action": "change_param",
      "field": "prepaid",
      "try_value": 15,
      "reason": "минимально допустимый аванс"
    }
  ]
}
```

**Список кодов ошибок (минимальный набор для MVP):**

| `error_code` | Когда возвращается | Поле `violated_rule` |
|---|---|---|
| `ADVANCE_BELOW_MIN` | Аванс ниже минимума для данной комбинации | `min_advance` |
| `ADVANCE_ABOVE_MAX` | Аванс выше максимума | `max_advance` |
| `TERM_ABOVE_MAX` | Срок превышает максимум для комбинации аванс+возраст | `max_term` |
| `TERM_BELOW_MIN` | Срок меньше минимума (обычно 12 мес.) | `min_term` |
| `CURRENCY_NOT_ALLOWED` | Валюта не разрешена для этого типа клиента | `currency` |
| `SUBJECT_NOT_ALLOWED` | Предмет не разрешён для этого типа клиента | `client_type` |
| `COST_OUT_OF_RANGE` | Стоимость вне допустимых границ | `cost` |
| `AGE_REQUIRED` | Для condition_new=0 обязателен age | `age` |
| `AGE_ABOVE_MAX` | Возраст предмета превышает максимум для лизинга | `max_age` |
| `SCHEDULE_NOT_AVAILABLE` | Выбранный тип графика недоступен для комбинации | `type_schedule` |

**Обязательное требование:** поле `suggestions` всегда содержит минимум один вариант корректировки. Это позволяет голосовому боту сразу предлагать клиенту решение, не перекладывая на клиента угадывание причины.

### 4.2 Валютная конвертация

**Текущее состояние:** API принимает только валюты, в которых физически оформляется лизинг. Для физлиц это только BYN.

**Предлагается:** добавить режим *"справочного расчёта"* с новым параметром `source_currency`. Клиент называет цену в любой валюте, API сам конвертирует по актуальному курсу НБРБ и выдаёт результат в целевой валюте.

**Пример:**
```
GET /1.0/calculate/?
  client_type=Физическое лицо
  &subject=Легковой автомобиль
  &cost=24300
  &source_currency=USD
  &target_currency=BYN
  &term=60
  &prepaid=20
```

Ответ содержит дополнительный блок:

```json
{
  "ok": true,
  "currency_conversion": {
    "source_currency": "USD",
    "source_amount": 24300,
    "target_currency": "BYN",
    "target_amount": 72900,
    "rate": 3.0000,
    "rate_date": "2026-04-16",
    "rate_source": "НБРБ"
  },
  "..."
}
```

**Почему это нужно на стороне API:**
- Курс НБРБ обновляется ежедневно. Хардкод на стороне бота устаревает сразу.
- Все клиенты API (голосовой бот, сайт, мобильное приложение) получают одинаковые цифры.
- Аудит: в ответе зафиксирована дата и источник курса, можно восстановить расчёт при споре.

**Временный MVP на стороне бота:** до реализации фиксированный курс 3 BYN/USD, с явным предупреждением клиенту *"курс 3 рубля за доллар ориентировочный"*. Это явный технический долг, который убирается после внедрения server-side конвертера.

### 4.3 Типы графиков платежей

**Текущее состояние:** параметр `type_schedule` принимается, но поведение неочевидно. Бот передаёт "1", получает тот же результат, что и при "0".

**Предлагается:**
- Явно задокументировать поддерживаемые значения: "0" = аннуитет (равные платежи), "1" = убывающий/линейный (равное погашение тела, убывающий процент).
- Если для данной комбинации параметров линейный график недоступен, возвращать ошибку `SCHEDULE_NOT_AVAILABLE` с указанием причины.
- В успешном ответе добавить поле `schedule_type_actual`, чтобы бот мог убедиться, что запрошенный тип был применён.

### 4.4 Аванс: проценты и рубли, вход и выход

**Текущее состояние:** `prepaid` принимает только процент. В ответе аванс уже посчитан в рублях (`advance_sum`), но клиент часто называет именно сумму ("аванс 15 тысяч"), и боту приходится самому конвертировать в процент перед вызовом API.

**Предлагается:** разрешить одно из двух полей на вход:
- `prepaid_pct` (число, 0-100) — если клиент назвал процент,
- `prepaid_amount` (число, в той же валюте что `cost`) — если клиент назвал сумму.

Взаимоисключающие, одно обязательно. API возвращает оба значения в ответе:

```json
{
  "prepaid_pct": 20.0,
  "prepaid_amount": 14000,
  "..."
}
```

Это устраняет класс ошибок "клиент сказал 15 тысяч, бот пересчитал в %, ошибся на копейку".

### 4.5 Матрица бизнес-правил (на основе Excel)

В файле *"Новые условия по лизингу с 01.04.2026"* содержится полная матрица:
`тип предмета × тип клиента × возрастной диапазон × тип продавца -> (мин. аванс, макс. срок)`.

**Пример фрагмента для легкового автомобиля, физлицо:**

| Возраст предмета | Мин. аванс | Макс. срок |
|---|---|---|
| Новый | 0% | до 24 мес. |
| Новый | 10% | до 60 мес. |
| Новый | 20% | до 84 мес. (BYN: не более 60) |
| До 5 лет | 10% | до 60 мес. |
| До 5 лет | 20% | до 84 мес. (BYN: не более 60) |
| 6-10 лет | 10% | до 48 мес. |
| 6-10 лет | 15% | до 60 мес. |
| 6-10 лет | 25% | до 84 мес. (BYN: не более 60) |
| 11-15 лет | 10% | до 24 мес. |
| 11-15 лет | 20% | до 60 мес. |
| Старше 15 лет | 10% | до 24 мес. |
| Старше 15 лет | 20% | до 60 мес. |

**Предлагается:** API владеет всей этой таблицей. При получении запроса с параметрами, которые ей не соответствуют, возвращает `ADVANCE_BELOW_MIN` / `TERM_ABOVE_MAX` с конкретной подсказкой из таблицы.

Дополнительные таблицы в Excel (грузовые, водный транспорт, спецтехника, оборудование, недвижимость) обрабатываются аналогично.

**Отдельный endpoint для справки:** `GET /1.0/rules/?subject=...&client_type=...` возвращает применимый фрагмент матрицы. Полезно для отображения условий на сайте и для голосового бота при консультативных вопросах ("а какой минимальный аванс для грузовика?").

## 5. Почему бизнес-логика должна быть на стороне API, а не голосового бота

Отвечаю на прямой вопрос: "где реализовывать быстрее и надёжнее, на системе или в калькуляторе".

### 5.1 Аргументы за сторону калькулятора

| Критерий | Обоснование |
|---|---|
| **Единый источник правды** | Excel-таблица это ваша бизнес-логика. Если её дублировать у нас, при изменении условий (что происходит регулярно) нужно координировать релизы двух команд. Ошибки и расхождения неизбежны. |
| **Переиспользование** | Сайт, мобильное приложение, CRM, голосовой бот получают одинаковую логику без дублирования. |
| **Атомарность обновлений** | Новые условия с 01.04, 01.07, 01.10 меняют данные в одном месте. Деплой в один сервис, все клиенты видят новые правила мгновенно. |
| **Аудит и воспроизводимость** | Ответы калькулятора можно логировать целиком. При споре с клиентом ("вы обещали 84 месяца") легко воспроизвести расчёт. На стороне бота сохраняется только текст диалога. |
| **Безопасность бизнес-правил** | Голосовой бот это тонкий клиент. Если он пытается сам рассчитать проценты, возникает риск расхождения с официальным расчётом, что создаёт юридические вопросы. |
| **Тестируемость** | API-уровень тестируется модульно: бросаем 10 000 комбинаций параметров, проверяем корректность. На уровне голосового диалога это практически невозможно. |

### 5.2 Аргументы за сторону голосового бота (которые мы отклоняем)

| Контраргумент | Почему отклоняется |
|---|---|
| "На боте быстрее изменить" | Быстрее в моменте, но создаёт технический долг. Через 3-4 таких "быстрых правки" бот и API начнут расходиться. |
| "API не наша зона ответственности" | Верно, но именно поэтому проблема вскрылась: бот-то готов, а API без структурированных ошибок не даёт боту работать корректно. Проблема находится на границе и решается на стороне владельца бизнес-логики. |
| "Конвертация валют простая, можно захардкодить" | MVP да. В продакшене курс меняется ежедневно и должен ходить в НБРБ. Это не должно быть ответственностью голосового бота. |

### 5.3 Что остаётся на стороне голосового бота

Голосовой бот отвечает за:
- Понимание реплики клиента (STT + понимание намерения).
- Извлечение параметров из свободной речи.
- Формирование человеческого ответа на основе ответа API.
- Удержание контекста разговора, профиль клиента в рамках сессии.
- Переспрос недостающих параметров.
- Отправка СМС со ссылкой на график.
- Эскалация на специалиста.

Бот не должен содержать бизнес-логику лизинга. Он должен быть "переводчиком" между голосом клиента и API калькулятора.

### 5.4 Сводная таблица распределения ответственности

| Область | Сейчас | Целевое состояние |
|---|---|---|
| Валидация параметров (аванс, срок) | Частично на боте (hardcoded "min 10%"), частично 404 от API | API возвращает структурированные ошибки с подсказками |
| Конвертация валют | Нет, физлицо + USD отказ | API, по курсу НБРБ, с аудитом |
| Матрица возраст/аванс/срок | Нет нигде | API, единая таблица |
| Тип графика (аннуитет/линейный) | Декларировано, не работает надёжно | API явно обрабатывает и подтверждает в ответе |
| Аванс в % и в сумме | Только % на входе | Оба варианта на входе, оба в ответе |
| Перевод ошибки в живую речь | Бот (останется) | Бот (останется) |
| Удержание контекста сессии | Бот | Бот |

## 6. Этапы внедрения (предлагаемый приоритет)

**Этап 1 (блокирующий голосовой бот, приоритет максимальный):**
1. Добавить структурированный JSON в любой неуспешный ответ (`error_code`, `message_ru`, `suggestions`).
2. Задокументировать фактически поддерживаемые комбинации параметров.

**Этап 2 (устранение ключевых функциональных пробелов):**
3. Реализовать фактическую поддержку `type_schedule="1"` (линейный график).
4. Внедрить матрицу бизнес-правил из Excel с точной валидацией на сервере.
5. Добавить endpoint `/1.0/rules/` для справочных запросов.

**Этап 3 (улучшение UX для физлиц):**
6. Серверная валютная конвертация по курсу НБРБ с параметрами `source_currency` / `target_currency`.
7. Аванс на вход в % ИЛИ в сумме (`prepaid_pct` / `prepaid_amount`).

**Этап 4 (долгосрочное развитие):**
8. Кеширование справочных запросов (TTL 24 часа).
9. Webhook уведомления при изменении правил (чтобы бот мог инвалидировать свой кеш).
10. Версионирование API: `/1.1/calculate/`, чтобы старые клиенты продолжали работать.

## 7. Примеры запросов и ответов

### 7.1 Успешный базовый запрос

**Запрос:**
```
GET /1.1/calculate/?
  client_type=Физическое лицо
  &subject=Легковой автомобиль
  &condition_new=1
  &cost=70000
  &currency=BYN
  &prepaid_pct=20
  &term=84
  &type_schedule=0
```

**Ответ (200 OK):**
```json
{
  "ok": true,
  "calculation_id": "56185628",
  "calculation_url": "https://mikro-leasing.by/graphic/?56185628",
  "currency": "BYN",
  "cost": 70000,
  "prepaid_pct": 20.0,
  "prepaid_amount": 14000,
  "term_months": 84,
  "schedule_type_actual": "annuity",
  "monthly_payment": 1598.69,
  "total_contract_sum": 151278.66,
  "increase_pct": 17.0,
  "buyout_sum": 0,
  "advance_sum": 14000,
  "payments": [{"month": 1, "sum": 1598.69}, "..."]
}
```

### 7.2 Отказ: аванс ниже минимума

**Запрос:** аванс 5% на легковой б/у 8 лет.

**Ответ (422 Unprocessable Entity):**
```json
{
  "ok": false,
  "error_code": "ADVANCE_BELOW_MIN",
  "message_ru": "Для легкового автомобиля 6-10 лет минимальный аванс 10%",
  "violated_rule": "min_advance",
  "rule_context": {
    "subject": "Легковой автомобиль",
    "age_bracket": "6-10 лет",
    "applicable_rules": [
      {"min_advance": 0.10, "max_term": 48},
      {"min_advance": 0.15, "max_term": 60},
      {"min_advance": 0.25, "max_term": 84}
    ]
  },
  "suggestions": [
    {
      "action": "set_prepaid",
      "field": "prepaid_pct",
      "try_value": 10,
      "resulting_max_term": 48,
      "reason": "минимально допустимый аванс для этого возраста"
    }
  ]
}
```

**Что делает голосовой бот с таким ответом:** читает `message_ru` + `suggestions`, озвучивает клиенту одной-двумя фразами: *"Для авто 6-10 лет минимальный аванс 10%. Могу пересчитать: аванс 10%, срок до 48 месяцев."*
